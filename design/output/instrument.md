# The instrument

Reader: whoever changes the display or its controls. Reference: [the Keysight panel the person shared](../input/images/2026-10-24-oscilloscope-keysight-dsox4104g.png).

**The page is an oscilloscope.** The trace display is always the main thing on screen; its controls sit to its right, grouped as on a bench scope: Run Control, Horizontal, Vertical. Setup happens in tabs below ([tabs.md](tabs.md)). It looks like a scope; where a scope's behaviour can be improved (direct manipulation, typed values, axis labels), it is.

## The screen is the record

What the screen shows is what is simulated and swept: from t = 0 to the right edge (horizontal position + 10 divisions). A simulation has no separate record length: **Save ▾** stores what the screen holds, every signal (below); only live data, which never repeats, also has a record of its own, the last minutes ([Save, the live record and references](#save-the-live-record-and-references)). The sweep crosses the screen at the header's **[Speed](#speed)**, 1× by default, real time: at 100 ms/div it takes 1 s (at 10×, 0.1 s), never faster than the page simulates the screen. While it sweeps, the current run is drawn only up to the scan line: what has happened so far. **Earlier runs stay, whole and fading**: the last run at 40 % strength, then 30, 20, 10, and gone after five runs, for every channel. So after an edit the old run shows what lies ahead and the new one can be compared with it. (The person, 2026-10-24.) Loading a project clears them. Stopped, the screen shows the whole last sweep.

## Display

- 10 × 8 divisions, dotted graticule with ticked centre axes. Time labels below the plot; the active channel's values on the left, in its colour (the active channel is the selected line, or else the Vertical channel). The margin widens to the longest value label, so a label such as −0.0121 keeps its sign.
- The screen is dark in both page themes; the panel around it follows the theme.
- Status line on top: run state, timebase, position, and which line is selected. Channel keys below: the same channel keys as under Vertical (lit in the channel's colour while it is on, the selected one marked under its number, the same press), each with its source and scale.
- A coloured marker in the left margin shows each channel's zero level.
- Hovering the plot shows a cursor with t and every active channel's value.
- **The scope's instant**, which the 2D views and the Analysis tab's Scope time follow: the time under the cursor where the screen shows time across (Time, Spectrogram) or the XY sample under it; else the sweep while running; else where the cursor last pointed (until the next run); else the right edge. In FFT mode the cursor is a frequency and does not move it.

## Direct manipulation

Every gesture sets the same settings as the knobs, and is undoable.

| Gesture | Effect |
|---|---|
| Wheel over the plot | Zoom time and all shown channels, around the cursor (the point under the cursor stays put) |
| Wheel over the time axis (below the plot) | Zoom time only |
| Wheel over the value axis (left of the plot) | Zoom values only |
| Click a trace or its marker | Select that line; drag and wheel now act on it alone (wheel zooms its values) |
| Click empty plot, or Esc | Release the line |
| Drag | Pan: sideways moves time, up/down moves all lines (or the selected one) |
| Shift + drag | Zoom to the marked box; a flat band zooms time only, a narrow band values only |
| Spectrogram, on the levels strip | Drag a handle or the band between them; wheel: floor, Shift + wheel: ceiling; double-click: automatic levels (the same as Run Control › Levels) |
| Spectrogram, the switch above the strip | Click: colour as absolute dB or as dB above the noise at each frequency (the same as Run Control › Colour) |

Wheel and knob zooms step 1-2-5; a box zoom shows exactly the marked region.

## Channels (Vertical)

Four channels, in the classic colours: 1 yellow, 2 green, 3 blue, 4 magenta. Each has a source, an on/off state, a scale (units per division) and an offset.

- **A channel's source is any Source or Sink in the plant diagram** (at any depth), picked under Vertical › Source, and nothing else: the list holds only names the person made in the diagram, each with its unit. Once a controller exists, its signals join. (The person, 2026-10-24.)
- **Every signal has a unit**, set on its Source or Sink (default `1`, unitless); badges, readouts and the source list show it.
- **Channel 1 shows r; channels 2–4 start with no source ("none").** Nothing the person adds is put on the scope by itself. (The person, 2026-10-24.) Picking a source switches the channel on; "none" switches it off. A closed-loop system from the library starts with r, y, u, e.
- A channel whose source has no data shows "no signal" and draws nothing.

- A channel key selects that channel for the Vertical knobs; pressing the selected channel's key again turns it off; pressing an off channel turns it on and selects it. The keys under the screen are the same keys and do the same (decisions.md, v2.7 after review).
- **Scale** knob: 1-2-5 steps. **Position** knob: 0.1 division per detent; double-click (the knob's push) sets it to 0.
- **Measure** key (Vertical, beside R axis): a Measure line under the screen for the selected channel ([below](#measure)).

## Measure

(Research: [sliding-mode.md](../research/sliding-mode.md), Recommendation 5: "hard on the actuator" has to be a number the person reads, not an impression of a dense trace.) Measure is **off by default, always** (the person, [input 42](../input/2026-10-25-42-measure-off-by-default.md): it clutters the traces, and the legend has the values); no library system opens with it on. A channel with Measure on gets **one line under the screen, in its colour**, in every display mode. The plot gives up 15 px per line. The line covers the samples the screen shows: inside the timebase window, up to the sweep while it runs (the samples XY draws), the display-filtered signal when the channel has a filter. A channel that is off shows no line; its Measure stays on, so the line returns with the channel.

| Value | Definition |
|---|---|
| mean | (1/n)·Σx |
| rms | √((1/n)·Σx²); for a current i through R, the heat is R·i_rms² (R read from the armature block) |
| ac | √((1/n)·Σ(x − mean)²): the rms of what moves |
| p-p | max − min |
| TV | Σ\|x_j − x_(j−1)\| / (t_last − t_first), the total variation per second: how far the signal travels, the actuator's wear (the repository's uTV, per second so windows compare) |
| rev | reversals per second: how often x turns after moving more than h, an edge count with hysteresis as bench scopes offer it (PicoScope); h = 0.1 division (the channel's scale / 10), shown in the line |

Example, the sliding-mode motor's relay over the whole run at 5 V/div: `3 V  mean 0.193 V  rms 11.7 V  ac 11.7 V  p-p 24 V  TV 2.79 kV/s  rev 116/s (h 0.5 V)`. Values below a thousandth of the channel's scale read 0; SI prefixes from below 0.1 and from 1000 up.

**Under-resolved.** RMS, ac and p-p of a waveform that is not resolved are wrong: a relay-driven current sampled at 4 points per period reads 1.5× its true mean square. When reversals/s × record step > 0.2, fewer than 10 samples per period (two reversals per period), the line ends with "under-resolved: n samples per period" in amber. The sliding-mode system records at 0.25 ms so that its relay current (62.5 Hz: 64 samples per period) and the 250 Hz try-this (16) are resolved.

For agents and tests the lines are in the canvas's `data-measure`. Code: `src/ui/measure.js` (`measure`, `measureLine`), drawn by `src/ui/display.js`; tests in `test/smc.test.mjs`.

## Display modes: Time, FFT, Spectrogram, XY (the person, 2026-10-24)

Four keys under Run Control switch what the screen shows; the setting is part of the project (`scope.view`, [project-format.md](project-format.md)).

- **Time**: the default, as above.
- **FFT**: the amplitude spectrum (single-sided, Hann window, amplitude-correct: a sine of amplitude A reads A) of every shown channel, from what has run so far, so it fills in while the sweep runs. 10 dB per division against a reference level rounded up from the run's largest peak; the Nyquist frequency (half the scope's sampling rate) is marked; the selected channel's peaks are labelled; its display filter is drawn as a dashed response curve. Wheel, drag and Shift-drag act on the frequency axis.
- **Spectrogram**: the selected channel's short-time spectrum over the screen's time (frequency up the left axis, a heat map) with the channel's own time trace drawn over it against a **second axis at the right**. The wheel over the plot zooms frequency; over the time axis, time. Hovering reads t, f and the amplitude there (in the channel's unit and in dB). In the encoder example the error orders rise as straight lines from the origin, and the 6× line folds back at the Nyquist frequency (aliasing).
- **Spectrogram levels** (the person, 2026-10-24: "a histogram of the amplitudes where you can select the cutoff … see how PyQt graph does it"). A strip at the right edge of the screen, right of the second axis, after pyqtgraph's HistogramLUTItem: a **histogram of the amplitudes shown** beside the **colour bar**, both on one dB scale (dB of the channel's unit: 0 dB is 1 unit, as on the FFT's axis). The histogram counts every frame and frequency row on the screen, from the whole run, so it does not change while the sweep fills in (in Live, where each sweep is built from nothing, it counts the last whole sweep, and the frame length is that sweep's, so the colours hold still from sweep to sweep); its bars grow from the colour bar to the left, linear in the count, so the noise is the big hump and the lines the thin tail above it. Two handles set the **floor** (below it a bin is black) and the **ceiling** (above it a bin has the brightest colour); in between the colour follows the dB value. The handles carry their level in dB, and a faint line every 20 dB, labelled where there is room, shows where the noise's hump sits; the status line shows both levels and the ceiling in the channel's unit ("−32 … 30 dB · ceiling 31.9 rad/s"), and *auto* or *levels set*. On a screen narrower than 600 px the strip is 40 px wide instead of 60.
  - **Gestures**: drag a handle, or the band between them (both move); a press above or below the band takes the nearer handle to the pointer. The wheel over the strip moves the floor (2 dB a step), Shift + wheel the ceiling. Double-click: automatic levels again. Hovering the strip reads the level under the pointer (dB and the channel's unit), the share of the shown bins above it, and which rule set the automatic floor. Every change is undoable.
  - **Typed** (Run Control › Levels, shown in Spectrogram mode): the floor and the ceiling in dB, as on the strip, for the signal the spectrogram shows; ↑ and ↓ step 1 dB, Shift 10 dB; **Auto** (lit while the levels are automatic) returns to automatic levels. While automatic, the fields show the levels in use.
  - **Automatic levels** (the default): the ceiling at the largest amplitude shown; the floor 10 dB above the median of the shown bins. Most bins of a spectrogram are noise, so their median is the noise's level; a bin of white noise lies 10 dB above its median 0.1 % of the time (its amplitude is Rayleigh distributed: 6.3 dB above the median at the 95th percentile, 10 dB at the 99.9th), so the noise turns black and whatever stands 10 dB above it stays. The floor stays between 20 and 80 dB below the ceiling: 80 dB was the scope's fixed depth before, and 20 dB keeps a picture of noise alone showing its noise rather than a few specks. Bins that are exactly zero (−240 dB: a noise-free signal has many, the *Mass–spring–damper*'s F 7020 of 7670) say nothing about the noise and are left out of the median and of the strip's dB range; the histogram still counts them among the bins shown. Zooming the frequency recomputes the levels for what is shown.
  - **Checked on *Encoder errors and torque ripple*** (`test/spectrum.test.mjs`): 7670 bins on the screen (118 frames × 65 rows), median −42 dB, so the floor is at −32 dB; the ceiling is at 30 dB (32 rad/s), the low-frequency burst of the run-down at the right edge (4.52 s, 3 Hz; before the run-down, [inputs 50–52](../input/2026-10-25-52-a-spike-only-at-the-start.md), it was the 2× line flaring at the resonance, 20 dB, so the lines now look a little dimmer in Absolute). The 1× and 2× lines and the 70 Hz resonance are above the floor on every frame, the 6× line up to 100 Hz; 36 % of the bins are above the floor, against 59 % with the old 80 dB range (71 % before the run-down), and the speckle between the lines is gone. The noise here is coloured (about −20 dB at the lowest frequencies, −85 dB near 200 Hz), so no single floor removes it and keeps the 6× line above 100 Hz, which is weaker than the low-frequency noise (−31 dB at 111 Hz, −47 dB at 196 Hz, −57 dB where it folds back). Ways to see it, in the example's notes: switch the colour to **Above noise** (below), which shows the whole line at once; zoom the frequency axis to 100–200 Hz, where the automatic levels become −53 … −2.5 dB and show 6× up to the Nyquist frequency and its turn there, with the 3× and 4× orders; or drag the floor down to about −60 dB to see the whole fold-back.
  - The levels belong to the scope view, **per signal** (`scope.view.levels`, [project-format.md](project-format.md)): dB of rad/s are not dB of V, so levels set on one signal do not carry over to a channel showing another, which keeps its own (or automatic) levels; back on the first signal, its levels return. They stay when the display mode changes, are saved with the project, and apply while the sweep runs and when stopped.
  - **The FFT view is unchanged** (interpretation): there an amplitude is a height, not a colour, so noise does not hide a line; and an FFT bin's noise level depends on the record length (an amplitude spectrum, not a density), so the spectrogram's dB levels would not line up with it.
- **Spectrogram colour: Absolute or Above noise** (the person, 2026-10-24: "keep the automatic flow as the default … but the delta mode, I like that. Like dB above the local noise, I like that. Maybe you can make that switchable. Make that a switch."). A switch, in Run Control › Colour (beside the Levels, shown in Spectrogram mode) and above the levels strip (a small key reading *abs* or, lit, *noise*):
  - **Absolute** (the default): as above, a colour is dB of the channel's unit, the same at every frequency.
  - **Above noise**: a colour is **dB above the noise at that frequency**: 0 dB is the noise there, +20 dB a line standing 20 dB out of it. Where the noise is coloured (strong at low frequencies, weak at high ones, as in a motor's speed), a weak line where the noise is low shows as well as a strong one where it is high; the price is that a colour no longer says how large the amplitude is (hover for that).
  - **The noise at each frequency** is estimated from what is on the screen (`spectrogramNoise` and `noiseLevel` in `src/core/spectrum.js`): (1) each frequency row's level over the frames on the screen, robust to lines: not the plain median, because orders that sweep slowly (or many that pass) cover more than half of a row's frames; it starts at the row's 10th percentile, lifted by 8.2 dB to where the median of noise lies, then takes the median of the values below that + 8 dB, four times, so a line 20 dB up is left out while it covers up to about 80 % of the row's frames; (2) a running median of those over ±4 rows as a first guess, so a line that stays at one frequency (a Hann main lobe is 3 or 4 rows wide) does not count either; (3) rows more than 6 dB above that guess are such lines and are bridged by a straight line (in dB) between the nearest rows that are not, and the guess is made again from the bridged rows until no row is added (a cluster of lines, or a wide one, lifts the first guess over all of them; where the noise falls steeply a line would lift the median of its window); (4) a running median over ±4 rows again and a mean over three rows, both centred, so the estimate is smooth and a slope is not bent at the ends. The same is done on a **second spectrogram with a Blackman window** (same frames and rows; ±6 rows, its main lobe is wider; less 0.6 dB, its wider noise bandwidth), and each row takes **the lower of the two**: a line only ever lifts an estimate, and the two are lifted by different things: a strong steady line spills over the rows around it through a Hann window's sidelobes (31 dB down: a sine 75 dB above the noise, between two rows, lifted the Hann estimate 45 dB there), much less through Blackman's (58 dB down), while Blackman's wide main lobe lifts the rows beside a moderate line, which Hann's leaves alone. The DC and Nyquist rows (one-sided bins) keep their own level. Every frequency row counts whatever the frequency zoom, so zooming does not change the noise; panning or zooming time does (other frames are on the screen). Exact zeros are left out, as for the levels, and **a row whose frames are mostly exact zeros has no noise**: in a noise-free signal (a reference made of steps, a disturbance that is off most of the time) a step's own frames would otherwise be its "noise", and the steps would turn into bright bars. **When no row has noise, the colours stay absolute**: the switch stays lit, the status line says *no noise: absolute*, the switch's hover says why, and the strip and the typed levels set that signal's absolute levels (the ones drawn) (in the library: the steps of r and d, which most systems have).
  - **The strip, the levels and the status line work in that unit**: the histogram counts dB above the noise (the noise is the hump around 0 dB, whose line is drawn a little stronger), the handles and labels carry a sign (+6, +68), the hover reads "dB above the noise" (or "3 dB below the noise", not "−3 dB above"), the plot's hover adds the bin's dB above the noise and the noise there ("+3.9 dB above the noise (the noise: −35.2 dB)"). The switch's hover, as the strip's, is beside the strip, outside the screen. **Automatic levels**: the floor **6 dB above the noise** (a bin of noise lies that far above its median 5 % of the time; the point of this view is to find weak lines, and those few bins get the darkest colours when a line stands well out), the ceiling at the largest value shown, the same 20 to 80 dB range rules as Absolute (noise alone: the floor 20 dB below its largest bin, so noise shows as noise). The status line says **Above noise** (a lit tag) and the levels ("+6 … +68 dB · auto"), or **Absolute** before the absolute levels. On a phone (narrower than 560 px) the status line takes two lines, the display growing by one so the screen keeps its size, and leaves out the absolute ceiling in the unit (the strip's hover has it).
  - **Levels set by hand are kept apart per unit, per signal**: dB above the noise are not dB of the unit, so switching shows the other unit's levels (or automatic ones) and switching back returns them (`scope.view.noiseLevels` beside `scope.view.levels`). The **switch itself is one for the whole view** (`scope.view.aboveNoise`, interpretation): it is a way of reading the picture, like the FFT's dB or linear, not a property of a signal. It stays when the display mode or the channel changes and is saved with the project.
  - **In Live** the noise comes from the last whole sweep, as the levels do: while a sweep fills in, its colours are measured against the previous sweep's noise, so they hold still from sweep to sweep (checked with the HIL plant: the levels change only when a sweep starts).
  - **Checked on *Encoder errors and torque ripple*** (`test/spectrum.test.mjs`): against the noise alone (the same system with the ripple and the encoder errors switched off) the estimate is within 4.2 dB on every row from 3 to 197 Hz but the resonance's (on average 1.4 dB, measured before the run-down): about −31 to −35 dB at the lowest frequencies (−34.8 dB at 37.5 Hz, where the noise alone is −38.7 dB; the first version read −21.1 dB there, because the orders cover more than half of those rows' frames) and −75 dB near 200 Hz. The 70 Hz resonance is part of the noise alone; it is bridged as a line (its hump stands 16 dB above the estimate) and shows on 116 of 118 frames. The automatic levels are +6 … +68 dB. The 1× and 2× lines show on every frame; the 6× line on every frame up to the Nyquist frequency (68 of 68) and back down after it folds (33 of 33), where in Absolute the same line above 100 Hz is above the floor on 6 of 70 frames. The 3× order shows on 99 of 101 frames, 4× on 87, 5× on 72 (both are weak where they cross 30–60 Hz: 4× there on 6 of 17 frames, the others within 6 dB of the noise); 15 % of the noise bins were above the floor before the run-down, partly the skirts of the strong 1× and 2× lines. Before the run-down the screen ended steady, and there (time zoomed to 4.5–5 s) the 6× line at 114 Hz showed on 8 of 9 frames beside the 2× and 3× lines, whose Hann spill-over hid it from a Hann-only estimate (0 of 9); those 0.5 s are now the run-down, where a Hann-only estimate shows it too, and the steady lines below hold the Blackman pass to it. Weak lines (10–20 dB above the noise) are dark purple against a ceiling of +64 dB: drag the ceiling down to brighten them. With sines in coloured noise falling 80 dB across the band, each 25 dB above the noise at its frequency, every sine is above the floor on every frame in Above noise, the noise estimate within 2 dB of the noise alone, and the two highest are below the floor on every frame in Absolute. Steady lines in white noise (`test/spectrum.test.mjs`): three lines two rows apart, a weak line three rows from a strong one, and a line in row 2 leave the estimate within 3.5 dB of the noise, a line 50 dB up between two rows within 4 dB, a line 75 dB up between two rows within 20 dB (Hann alone: 45 dB).
- **XY**: channel 1 drives the beam across at its own scale, the other shown channels draw against it, as on a bench scope; the beam draws the samples inside the timebase window, so moving the window past the start-up leaves the settled figure. The **Δ** key (shown in XY) makes every channel in channel 1's unit draw channel 1 minus itself: with r on 1 and y on 2 that is the error e = r − y over r, the person's plot ("ideally a line, usually an ellipse"): perfect following is a flat line, a gain error tilts it, a lag opens it into an ellipse. Each figure reads out its best line Y ≈ a·X + b and its spread σ around it (σ ≈ 0: a line); a slope or intercept below a millionth of a division reads 0. Wheel, drag and Shift-drag on the screen act on the Y channels (the selected one, if a Y channel is selected), below it on channel 1; channel 1 is never moved by a gesture on the screen, and a line 1 selected in Time is released on entering XY. Hovering marks the figure's sample nearest the pointer with its time. Auto Scale fits the Δ figure. A channel that switches between X − Y and itself (changing the mode or Δ) is fitted again, so pressing Time on *Following a sine* shows the angle at its own scale, not at the error's. The status names Δ only when it changes a channel ("Δ: no channel in N" otherwise), and with channel 1 off or without a source the screen says which. It sits on the display rather than the Analysis tab because it needs no linear model and works for any plant (research: [analysis.md](../research/analysis.md) §6). Example: *Following a sine (XY)*.
  - **The phase portrait is XY without Δ** (*DC motor, sliding mode*): the error e on channel 1, the speed on channel 2. While r is held ė = −ω, so a sliding mode's line s = λ·e + ė = 0 is speed = λ·e, a slope of +λ through the origin; the beam runs along a reaching arc at full voltage, then along the line. The readout's slope a reads λ in a window that starts after reaching (100 ms/div at 0.4 s: 9.89 for λ = 10; the whole run gives about 7, as the line also fits the arcs), and σ, the rms vertical residual, is then the rms of s: the band the motor slides in, in rad/s. With the scales in the ratio λ (0.1 rad/div, 1 rad/s/div) the line rises one division for each division across (not 45°: a division is wider than it is tall). Δ stays off: e (rad) and the speed (rad/s) differ in unit.
- **Display filters**: each channel can have one (Vertical › Filter: low-pass or high-pass Butterworth of order 2–8, band-pass, notch), applied live in every mode: the scope shows and analyses the filtered signal; the system is not changed. The wheel over its frequency sweeps it. Implemented in `src/core/spectrum.js` (second-order sections, bilinear transform with prewarping).
- **R axis**: one channel can have its values on a second axis at the right of the screen (Vertical › R axis); the left axis then shows another channel.

Code: `src/ui/freqview.js` (drawing, caching of filtered signals and spectra, the levels strip and its switch), `src/ui/xyview.js` (XY), hooks in `src/ui/display.js` (layout, the strip's gestures, the switch, the status line); the levels' arithmetic (histogram, automatic levels, the strip's dB range, the noise at each frequency and dB above it) in `src/core/spectrum.js`.

## Horizontal

- **Scale** knob: seconds per division, 1-2-5 steps. **Position** knob: the time at the left edge; double-click sets it to 0.

## Readouts

Every knob has a readout below it. Click it to type a value: `20m`, `100 ms`, `2u`, `-0.4`. Typed values need not be 1-2-5.

## Run Control

- **Run/Stop**: lit green while running, red while stopped. Stop freezes the sweep, not the data: edits still show at once.
- **Single**: from Stop, one sweep from the start of the screen (t = 0 at position 0), at the [Speed](#speed), then stop; lit amber meanwhile. The plant's view replays it (the pendulum drops again). **Pressed while running, the sweep under way finishes and then the scope stops**: no jump back to the left edge (the person, [input 10](../input/2026-10-24-10-sliding-mode-and-triple-swingup.md): "if I press the single button while something is already running, then I actually just want the current run to finish … Especially in hill mode"). `singleFrom` in `src/core/speed.js`; the sweep clock already stops a Single at the right edge. With a live plant, Run, Stop and Single go through the plant ([Live](#live-an-external-plant)).
- **A project or system may say how it opens** (`ui`: run state, tab, view, setup height); the System library's systems open running on their view in the Plant tab, except the badly tuned oven, which opens on the Auto-tune tab, and the two live systems, which open stopped: nothing runs until the plant is connected and Run is pressed ([project-format.md](project-format.md), [hil.md](hil.md)).
- **Auto Scale**: the timebase shows one period of the input (the smallest 1-2-5 step whose 10 divisions hold the period, position 0); each channel with a signal is scaled to about 6 divisions and centred on a whole division. The channels showing a Controller block's r and the y it compares with r share one scale and offset (if they have one unit), so the reference and the output that follows it overlay (r and T of the oven); nothing else is grouped, and XY mode is left alone ([autotune.md](autotune.md)).

## Speed

The person ([input 10](../input/2026-10-24-10-sliding-mode-and-triple-swingup.md)): "we're going to have to add time control, and we can probably add that to the header bar. And then normally it is 1x, but we can also increase it to like 5x or 10x or infinite. Like, I guess make it optional how many x you want, allow infinite, like with a -1 would be infinite. And also show how fast the time is actually running. So we can see when, if I set to infinite, I see, okay, it caps out at 20x. And then the fast toggle of the autotune, that would go away. … for the hill, in hill we are fixed to 1.0. And when we say we allow arbitrarily fast times, the user could also enter 0.1, right?"

**Speed, in the header bar, sets how fast simulated time runs: simulated seconds per wall-clock second.** Every clock of the page runs at it: the sweep, Auto-tune's runs ([autotune.md](autotune.md#the-tab)); **no speed runs faster than the page simulates the screen**, and ∞ runs at that; a live plant holds it at 1×.

- **The control**: the factor in a field (1× by default) and **▾** with presets: 0.1× (slow motion), 0.5×, 1× (real time), 2×, 5×, 10×, **∞** (as fast as possible). Type any positive factor (`5`, `0.1`, `20x`, `2,5`); `-1`, `inf` or `∞` is as fast as possible. Anything else (0, other negatives, words, a number too large to hold such as `1e400`) is refused with a toast and the speed stays. The field shows up to six digits and is wide enough for them (`123456×`, `0.0001×`, `0.333333×`). Interpretation: the presets are the person's 1×, 5×, 10×, ∞ and 0.1×, filled in with 0.5× and 2×.
- **Keyboard**: in the field Enter sets, ↑ ↓ step through the presets at once, Esc goes back to the speed from before the field took the focus (what was typed and the arrows' steps); on ▾, ↓ or Enter opens the presets with the current one focused, ↑ ↓ Home End move, Enter or Space picks, Esc closes (focus back on ▾). Keys typed in the field are not scope shortcuts. One header menu is open at a time: opening Speed ▾, System library ▾ or Save ▾ closes the others.
- **Saved with how the page is set**: `ui.speed` in the project (a positive number, or -1 for ∞; [project-format.md](project-format.md)), so Save, Export HTML and the autosave keep it and opening a project applies it. A project without it leaves the speed as it is (the System library's systems carry none). The autosave is also written when the page is closed or reloaded, so a change just made is not lost.
- **Beside it, the speed achieved**, measured, not assumed: the simulated time that really ran over the wall-clock time it took, over a moving window of the last second, updated four times a second ("9.8×", "12×", "0.10×", whole numbers from 100×). A pause between two of Auto-tune's runs counts, and so do frames slower than four a second; so a slow page reads below the setting. "–" when nothing has run for a second (the scope stopped). Its tooltip gives the simulation's speed (below) and says when the setting is held to it; the readout is then a shade darker.
- **The simulation's speed** (`app.simRate` in `src/ui/app.js`): the screen's simulated seconds over the wall time its simulation took, timed every time the screen is simulated (after each change). A screen simulated in under 2 ms is run a few more times so the timing is longer than the clock's resolution. The first simulation of a system is slowed by the browser compiling it, so while the speed is held to this figure it is timed twice more, a second apart, and the fastest timing counts. **No speed runs faster** (`paceOf` in `src/core/speed.js`), and **∞ runs at it**: so the readout at ∞ shows the page's limit for this system on this screen, the same thing Auto-tune's ∞ shows by computing every run. It depends on the screen: the simulation takes the same number of steps (2000) for any screen, so a finer time per division costs more per simulated second. A screen the page simulates slower than real time (a 10 ms screen of the oven: 5 µs steps, 0.7×) runs below 1× at every setting, and the readout says so. Interpretation (after review; see decisions.md): before, ∞ swept a screen per frame, so its figure was the screen's length times the frame rate, not a limit of the system.
- **The sweep clock** (`sweepClock` in `src/core/speed.js`, a pure function of the scan line, the window, the pace and the wall time since the last frame): the scan line advances pace × wall time each frame; a frame counts at most 0.25 s of wall time (a hidden tab or a stall does not throw the sweep forward; a page drawing fewer than four frames a second falls behind at 1×, and the readout shows it). **A finite pace keeps time across sweeps**: what is left of a frame when a sweep ends goes on into the next, round the screen as often as it takes (at 1× a 10 ms screen ends a sweep or two in every frame), and all of it counts, so 1× is real time on every screen the page simulates faster than real time. A Single stops at the right edge. Only without a timing (none yet) does ∞ complete the sweep in the frame.
- **Interpretation, said plainly**: the simulation computes the whole screen at once after each change (the screen is the record), and each sweep replays it, since a simulation run twice gives the same run. The sweep is paced as if it were being simulated, at no more than the simulation's own speed, so the readout tells how fast this page can run the system, as the person asked ("show how fast the time is actually running").
- **Everything keeps working at every speed**: Run, Stop (Run goes on from where it stopped), Single (one sweep at the speed: 50 s at 0.1× on a 5 s screen, a few frames at ∞), the fading of earlier runs, Save ▾ › Screen, references, the 2D views (they follow the scan line), and the FFT, Spectrogram and XY modes (they show what has run so far).
- **Earlier runs at ∞**: a sweep fades the earlier runs a step, as at any speed, but at ∞ the same run comes round many times a second, so there only a changed run becomes an earlier one; after an edit the run before it stays faded to compare with, and after Auto-tune at ∞ the run it started from stays. Interpretation (after review): at a finite speed every sweep still fades them (at 100× on a 5 s screen the old run is gone in about 0.2 s; whether to count only changed runs at every speed was asked and answered: no change, earlier runs stay visible as they are and levels or edits are compared with Single runs; input 13).
- **Live**: while a plant is connected the control is held at 1×: the field is read-only in the secondary ink, a lock shows at its left, ▾ opens nothing, and a click or tap on either says why in a toast ("the external plant owns the clock"; also the title). The setting comes back on Disconnect. The readout then shows the plant's clock against the page's, from the time stamps of the plant's messages: "1.00× live" ([hil.md](hil.md#timing)); it keeps a fixed width, so nothing moves when it changes.
- For agents: `window.loopTuner.speed(x?)` sets it (a factor, or -1) and returns `{ speed, effective, achieved, simulation, locked }` (-1 for ∞; `simulation` is the simulation's speed, or null; `locked` is why it is held at 1×, or null).

Code: `src/core/speed.js` (parsing, `paceOf`, the clock, the meter; tests in `test/speed.test.mjs`), `src/ui/speed.js` (the control and the readout), the timing in `src/ui/app.js` (`acquire`, `app.simRate`), the sweep in `src/ui/display.js` (`frame`).

## Live (an external plant)

A system with an External plant block runs against a plant outside the page ([hil.md](hil.md)). Run Control stays the scope's: its Live controls (**Download the plant (zip)**, **Connect / Disconnect**, **Reset**, **Hold**, where the plant listens, the link's state, Live settings) are in the Plant tab's right-hand panel, and a red **E-STOP** sits in the header beside the System library (key `E`), reachable from anywhere (the person, input 10: "I'm not sure if I want the hill stuff in the Ostsee controls. Just put them in the plant controls in the bottom right corner"; "put it into the header bar, right in the middle, next to system library").

- **Nothing runs by itself** (the person: "even when you have connected, you still need to press the run button so that we actually start"). Offline the scope stands still and says OFFLINE, with nothing on the screen: the diagram is not simulated against a plant that reads 0. Connect only opens the link. **Run** starts the plant and the sweep, **Stop** stops both, **Single** runs one sweep and stops the plant (pressed while running, the sweep under way finishes first). Run or Single offline, or with an E-stop latched, is refused with a toast saying what to do.
- **Hold** (`H`, or the Live panel's Hold key) freezes the screen while the plant runs on; the live record goes on. The status line says HOLD; `H` again releases it. This is how the screen is frozen now that Stop stops the plant.
- **Every live signal has a full scale** (the plant's min … max, or the full scale of what a reference drives or is compared with); the channels showing them span it, 8 divisions, when the system loads and when the plant brings other ports; Auto Scale offline does the same, live it fits the sweep.
- **Before every loop the references ramp in** to the waveform's first value at no more than 10 % of full scale per second; the first ramp is drawn as a sweep of its own (from the left edge, then faded behind the loop), and the status line counts it down: "ramping to r0: 2.1 s left".
- Live data sweeps the screen as a simulated run does: at position w0 a run's time w0 … w0 + W (counted from the loop's start, after the ramp-in) is drawn where the axis says, later screen widths sweep the same window again, and earlier sweeps fade. The status line says LIVE (with the plant's time), CONNECTED, E-STOP (with the reason), HOLD or OFFLINE, and carries `data-run`, `data-live` and `data-ramp`. While connected the [Speed](#speed) is held at 1×: the plant owns the clock. The header's E-STOP sits between the System library and Undo, after the Speed group and its separator, so both read clearly.

## Save, the live record and references

Under the screen, beside the channel badges, like a scope's save keys. Storing traces is a general scope feature (the person: "if we set our oscilloscope to 50 seconds and we measure a 50 second thing … I want to be able to store that … either as a screenshot or as … data … if there are 20, then we store all 20").

- **Save ▾ › Screen**: what the scope acquired over the screen's window, **every signal** of the system (every Source and Sink, not only the four on channels): a simulated run, or the live sweep on the screen (its time is screen time; the file says the offset to plant time). **CSV** (`t [s]`, then every signal as `name [unit]`; a `#` line says what it is; a UTF-8 mark first, so spreadsheets read units such as N·m), **JSON** (`format`, `title`, `source`, `units`, `t`, `signals`), or **Copy** (CSV to the clipboard). **Screenshot (PNG)**: the scope as it is, the title and the status line (its tags in their colours), the screen and the channel badges, on the display's own background (the theme's), at the device pixel ratio; **Copy image** puts the same picture on the clipboard where the browser allows it (else a toast says to use Screenshot). Both are there even before anything has been swept.
- **Rec** and **Save ▾ › Live record**: for a system with an External plant, the last *length* of every live signal (5 min unless set; click the length to type 30 s, 10 min, 1 h; kept per viewer). (The person: "if I set a trace to 5 minutes, I should be able to store that".) It runs across Run, Stop and reconnects on one real-time axis: each run's samples keep the plant's time, placed when the run started, with a gap while the plant was stopped. A Sink added while live gets a column of its own (empty before). It holds up to 2²⁴ numbers (128 MB) in all; the tooltip says how long that lasts at the current rate when it is less than the length. Simulated data is not recorded here: a simulation repeats the same run, which the Screen already holds whole. (Changed after review: the first version appended every simulated sweep into one long, misleading record.)
- Files leave through the page's one download path, `app.download(name, data, type, hint)`: the host's download capability where the page has one (the claude.ai viewer, which asks the viewer to confirm), else a download link. There is no viewer-specific variant: wherever a file can leave (a plain browser, or a host with downloads; `app.canSave()`), every key is offered. In a frame where no file can leave, the file keys (CSV, JSON, Screenshot) hide, as the header's Save JSON and Export HTML always have there, and the Copy keys remain; a save tried anyway (from the API, or the plant's zip) says in a toast what to do instead (`hint`: Save ▾ › Copy, Copy image, Copy HTML, `loopTuner.live.plantFiles()`). (After review, 2026-10-25: it said "use Copy JSON or Copy HTML" for a trace too, which copies the project, not the trace.) Long records are written in parts, never as one string.
- **Open…** reads a saved trace (CSV or JSON; any CSV whose first column is time) and draws it **dashed** on every channel showing a signal of the same name, until cleared (**ref ✕**). A trace with any part in the window is drawn at its own time (one saved from the same screen lines up exactly); one outside it, such as minute 5 of a live record, is folded in like a live sweep, its first sample at the left edge. **◀ ▶** move it by a screen width through a trace longer than the screen; the toast and tooltip say which part is shown. References never fade (earlier runs do); several can be open.
- For agents: `window.loopTuner.record` ([hil.md](hil.md#for-agents-through-the-browser)).

## Knobs

Endless rotary encoders, like a scope's: every detent is one step. Drag up or right to turn clockwise, scroll, or use the arrow keys when focused.

## A limited environment

Where the page runs in a limited environment, such as a file preview's sandbox (SharePoint's HTML viewer), a warning shows right below the header, full width, filled in the warning lamp's colour (a `.banner` with `data-lamp="warn"`, design-system.md), with ⚠ and the words "Warning: limited environment". It says the performance is degraded, names what is lost there (saving and the autosave, downloads, Live/HIL, possibly the speed), what was found, and what to do: **download this file and open it in your browser**. It stays visible the whole time; there is no hiding it. Everything that works there keeps working. It sits in the header's flow, so it covers no control, and it wraps at phone width.

- **It is in the page's HTML from the start**, so it shows where no script runs. An inline check before the first paint hides it where the environment is full, so it never flashes. The page's start then fills in the reasons (`src/ui/limited.js`; `loopTuner.limited()` returns them).
- **The rule.** In a known host (the hosted build's `window.__ltHost`), never limited. Otherwise limited by any of these: an opaque origin in a frame, or served from a site (a sandbox without `allow-same-origin`; a file opened directly also has one, and does not count); no localStorage in a frame; a readable frame `sandbox` without `allow-downloads`; a Blob worker that cannot be made, or that fails at once (a `worker-src 'none'` policy). No storage in a window of its own (a private window, a browser setting) does not count: the page is already open directly.
- Checked in a browser by `node tools/limited-check.mjs` (normal, sandboxed, a SharePoint-like policy, no JavaScript, a fully allowed same-origin frame, the hosted build). Research: [../research/limited-environment.md](../research/limited-environment.md).

## Layout

Two separators can be dragged: between the display and the setup tabs, and between the display and its controls. The sizes belong to the viewer (kept in their browser), never change when a tab changes, and double-clicking a separator resets it. The setup area starts at the height the Input tab needs, so nothing scrolls; the tab strip never scrolls.

## Keyboard

`R` run/stop, `S` single, `A` auto scale, `Esc` release the selected line; with an External plant `E` E-STOP and `H` Hold (not while typing in a field). Ctrl+Z / Ctrl+Shift+Z undo and redo. Digits belong to the numeric entry of the active tab. The Speed field and its presets take the keys described under [Speed](#speed).
