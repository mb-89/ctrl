# Designs computed in the page

Reader: whoever builds or changes a designed controller or observer, the plant model a design sees, the swing-up planner, or the Analysis tab. This is the decided architecture, condensed; the full plan, with the reasons, cost figures and test list, is [designs-in-the-page.md](designs-in-the-page.md). Where the code and this page differ, the code wins and this page is fixed.

**Nothing plant-specific computed offline is stored.** The project file, `plants.js` and the HTML hold design inputs only: weights, times, levels, limits, names, physics parameters, and gains a person chose by hand. Every gain, table, trim value, model and plan is computed in the page from the plant as it is wired, by code that ships in the bundle; Node runs the same code. (The person, [input 09](../input/2026-10-24-09-analysis-autotune-triple-swingup.md): "It should be computable in principle … the optimizer, it should be part of the package that we deliver, not something that you bake in.") The rules and interpretations are in [decisions.md](decisions.md), v2.7.

## Modules

| Module | Role |
|---|---|
| `core/diagram.js` | The compiler. In `model` mode it gives the plant a block sees (`el.seen`); in a normal compile it makes the laws once every node exists, observers first, and asks the design store for the values of each running designed variant (`el.designs`: their statuses) |
| `core/linearize.js` | `DesignError` (code, sentence, hint); operating points (`parseOp`, `opLabel`, `operatingPoint`), `trim`, `linearize` (with its `kinks`), `refuseKinks`, `firstOrderFit` (on a minimal realisation: linalg's `minreal`; rank checks on `equilibrate`d matrices), on a Model. Pure numerics |
| `core/planner.js` | The swing-up plan (`planTransfer`, a generator), the step map's Jacobians along it (`alongPlan`), TV-LQR gains (`tvlqrGains`), the plan in measurement order (`planValues`), the law that follows it (`planLaw`) and the closed-loop check (`verifyLoop`). Imports linalg only |
| `core/design.js` | Keys (`canonical`, `hashKey`, `plantKey`), the memory-only design store (`createDesignStore`, `SYNC_DESIGNS`, `useDesigns` and `defaultDesigns` for the page's guest compiles, heavy entries for plans), `lqrDesign`, `poleOf`, `piCancel`, `scheduledPIDesign`, `trajectoryDesign` and `kalmanDesign` |
| `core/controllers.js`, `core/observers.js` | Hand types unchanged; designed types `lqr`, `swingUpLqr`, `scheduledPI`, `trajectory`, `kalman` |

`design.js` never imports `diagram.js`: the diagram hands the store a closure that compiles the model (from a copy of the diagram, since the store keeps it). `DesignError` lives in `linearize.js`, the lowest module that raises one, because the bundle cannot re-export a name; `design.js`, the types and tests import it from there. Bundle order: `… goal, linearize, planner, design, controllers, observers, diagram …`.

## The plant a block sees

The map from a **cut** signal u to the block's **measurements**, evaluated by the same compiled `eval` as the simulation.

- **Cut**: a Controller's own output; for an Observer, the node wired into its input 1 (u), whose value is replaced by u.
- **Measurements**: what feeds the block's inputs 2…, in port order, labelled as the Controller tab shows them (`blockInputNames`).
- **Other Controllers** hold their output (0, or `at.held`). A cascade's inner loop is designed open, and the Model says so.
- **Observers**: a Kalman observer is looked through (estimate k reads the true state it stands for, `at.seeThrough`, from its design's `values.stateIndex`); any other observer's estimates are held, with a warning. Estimates beyond the states a Kalman observer sees stand for none and are held, with a note naming them.
- **Sources** read 0 (the nominal plant is undisturbed), or `at.sources[name]`.

### Model mode (`compileDiagram(d, 'plant', { mode: 'model' })`)

| Block | In model mode |
|---|---|
| Dead time, transfer function with delay | Pass straight through; each measurement reports the dead time on its way from u in `delay[k]`. If paths differ (a dead time in a loop or a parallel branch), only what every path has is reported, with a warning |
| Quantizer | Identity; its step goes into `sensors[k].q` when it sits between the plant and measurement k, times its gain to the measurement there (several add as root-sum-square), and is named in `sensors[k].parts` ("quantizer 'encoder' step 0.01 × 0.5") |
| Noise | Adds 0; its σ goes into `sensors[k].std` likewise ("noise 'jitter' σ 0.05 × 500" after a unit conversion). Noise on no measurement's way (on a torque, say) is process noise: a note, since no design accounts for it |
| Saturation, Function, Switch | As in the simulation, so finite differences see their slope; `limits(x, u)` lists the saturations outside their limits (no slope) or at a limit, within a difference step of it (the slope differs left and right: `edge`); `atLimits(x, u)` gives their sentences |
| Controller, Observer | No laws are built; outputs come from the cut, `held`, or the look-through |
| Source | `at.sources[name] ?? 0` |

When u reaches none of the measurements the Model says so, naming a held Controller in between. Errors (`no-block`, `no-cut` for an Observer with nothing on its u input, `bad-state`) carry `code` and `hint`, for `DesignError` to take over.

`opts.laws === false` is separate: the normal compile with every sampled block at u = 0 and no designs. The Plant tab's structure check uses it, so editing the canvas never designs.

### States and the Model

- **Global state order** is the compile's allocation order (diagram order, depth first through subsystems, then each block's own order), the same in both modes, so a simulation snapshot X fits a model directly. `el.states` lists every state with its label.
- **Physics blocks** declare `ode.states(p)` (cartPole `x, v, θ, ω`; pendulumCart `x, θ1…, v, ω1…`; conicalTank `h`) and `ode.make(p)`, which computes constants once and returns the allocation-free rate function the compile uses. The pendulum chain uses one sin and one cos per angle and solves its mass matrix by Cholesky (LDLᵀ).
- **A first-order transfer-function block** (integrator, first order) is realised with C = 1, so its state is its output: the state of "Motor/load" is the speed. Higher orders are labelled `name.x1…`.
- **Labels**: `subsystem/block.state` for states; measurements by what feeds the input.
- **Structural reduction**: the Model keeps the states that the cut reaches **and** that reach a measurement (a walk over the compiled nodes). The rest stay at the base state X0. Motor position: armature, load, angle; tank: h; carts: all.

The gain of a sensor block to its measurement, |∂y_k/∂(the block's output)|, is taken by one central difference of the measurement slice with that node's output moved, at the origin (where a Kalman filter is designed). The review found R 10⁶ off with a gain of 1000 after a noise block.

`el.seen(idPath, at)` (idPath: subsystem ids and the block id, `'motor/ctrl'`) returns, memoised per `at` (up to 16 per compile):

```js
Model = {
  idPath, name, kind,             // the block; kind 'controller' | 'observer'
  n, m, X0, x0,                   // kept states, measurements, full base state, kept base state (hanging for the pendulums)
  input: { label },               // what u is called ('F' when a Sink records it; for an Observer the Sink of what feeds its u)
  states:  [{ label, name, unit, angle, index }],   // index into the global state
  outputs: [{ label, angle, unit, state?, slope? }], // angle and unit when exactly one state at slope 1; state, slope when one state alone (trim starts there)
  f(x, u, dx), y(x, u, out),      // allocation-free; f evaluates only the nodes the kept rates read, y those the measurements read too
  limits(x, u), atLimits(x, u),   // saturations outside or at their limits there: { name, edge, sentence }, and the sentences
  delay: [s], sensors: [{ std, q, parts }], bound, warnings: [],
  through: [names],               // the observers it looks through (for the Analysis tab's notes)
}
at = { held?: { [idPath]: number | number[] }, sources?: { [name]: number }, X?: full state, t?, seeThrough?: Map(observerIdPath → global indices) }
```

## Operating points (`linearize.js`)

`operatingPoint(model, op, { umin, umax })` → `{ kind, x, u, y, drift, rest, label, warnings }` for:
- `'origin'`: x = 0, u = 0. `rest` is false (with a warning naming the fastest state) when max |f(0, 0)| > 1e-6; LQR then refuses (`not-at-rest`). The encoder example is such a plant: its encoder error is not 0 at angle 0.
- `'initial'`: the model's start state, with the u that comes closest to holding it (scalar Gauss–Newton). For the tank this is its PI's u0, a√(2g·0.15) = 0.1716, computed.
- `{ y: [...] }` (null leaves a measurement free): `trim`, a damped Gauss–Newton with minimum-norm steps over (kept x, u), so coordinates the levels leave free stay where they start (a cart moved to x = 0.3 keeps its pendulum hanging). Each residual row is divided by the size of its Jacobian row: that leaves the minimum-norm step as it is, but a stiff state's rate (the encoder's 1 ms filter after a 70 Hz shaft: 10¹¹ per unit beside 1) no longer drowns the rest in the damping. A residual counts as 0 within 1e-8 plus what a relative error of 10⁻¹² in z leaves of it. Starts, in order: (1) from the levels, where a measurement reads one state alone (`outputs[k].state`, `.slope`): that state at its level, the rest at the start state, u the input that holds that (an empty tank, h₀ = 0, trims at 0.1 m at once); (2) the start state with the input that holds it, not u = 0 (from u = 0 the tank's first step lands on a negative pump flow, where the pump has no slope); (3) from there in eight stages. A slope whose one side is not finite or flat (a pump at zero flow, √h at 0) is taken from the other side. Iteration caps only. Refusals: `trim-failed` ("no equilibrium with x = 0.3 m, θ = 0.5 rad: …"; the encoder at a constant speed of 100 rad/s, since its angle keeps growing), `u-limit` ("holding h = 0.98 m needs q = 0.438, above u max 0.3"). Limit: a saturation with no slope at the start (a valve shut below its lower limit) can hide an equilibrium.
- `{ t, u }`: a Model built at a snapshot of the run (`at.X`, `at.held`, `at.sources` from `simulateSystem(…, { until: t })`), u what the block put out there; not an equilibrium, so the drift is reported ("t = 1.70 s is not an equilibrium: tank.h moves at 1.93 m/s"); never in a variant. `linearizeBlock` builds it (below).

Labels read `origin (all states 0, u = 0)`, `h = 0.45 m, q = 0.297`, `t = 2.10 s of the run`; a measurement that is exactly one state carries its unit (`Model.outputs[k].unit`). `linearize(model, op)` by central differences (step 1e-6·max(1, |v|)) gives `{ A, B, C, D, n, m, states, outputs, input, op, delay, sensors, kinks, warnings }`, matrices as arrays of rows (B n×1, D m×1).

- **Kinks.** Each slope is also taken one-sided. Where the two sides differ by more than 10⁻³ (plus 10⁻⁶ of the row's largest slope and the rounding noise) and the gap does not shrink when the step is 10× longer (a smooth function's gap is its curvature times the step), `lin.kinks` says so ("the slope of the rate of cart and pole.v along F differs left and right (0 and 1)"; the empty tank: "… of tank.h along q differs left and right (0 and 127)"), led by the saturations at a limit there ("'amp' is at its limit at the operating point (input 0, limits 0 to 25): the slope differs left and right"). `refuseKinks(lin, what)` makes LQR, the Kalman filter and the PI design refuse with `kink`: the central slope there is neither side's (a one-way actuator at 0 halved B and gave K[θ] = −90.5 for −63.2; the tank at h = 0 gave a slope that depends on the step). The tank's wall top (h = H = 1) is no kink at an equilibrium: there it only bends the curvature.
- **`firstOrderFit(lin, k)`** keeps the states on the path from u to measurement k, reduces them to a minimal realisation (`minreal` in linalg.js: A balanced, then projected on Arnoldi bases of the Krylov spaces of B and of C_kᵀ; a direction weaker than 10⁻⁸·‖A‖ counts as cut off, above the error of the finite-difference slopes, so a pole and a zero that cancel in the plant cancel here), and gives K = D − C A⁻¹ B, τ = C A⁻² B / K, θ = delay. Refusals: `integrating-plant` ("angle integrates V") only for a pole at 0 left after that (the encoder without its ripple torque: the angle's integrator is cancelled by the derivative after it, and the speed has K = 20/3 times the encoder's slope), `unstable-plant` for a pole in the right half-plane ("the path from V to speed from angle is unstable: a pole at 11.4 rad/s": the ripple torque pushes the rotor away from θ = 0), `zero-gain`, `no-path`. Rank checks elsewhere (LQR's C) are made on `equilibrate`d matrices, powers of 2 per row and column.
- At a kink exactly on the operating point the slope is accurate to about 10⁻⁶ only (the tank's Ki at 1 m is off by 9·10⁻⁷; elsewhere 10⁻¹⁰). A badly scaled state also takes too long a step: the encoder's shaft state x2 (its output is wn²·x2) moves the angle 0.19 rad per step, which puts its slope 4·10⁻⁴ off. Variants take no operating points in v1: LQR and Kalman at the origin, the tank PI at trim points of the level.

## The swing-up plan (`planner.js`)

`planTransfer(model, { T, Ts, segments = 12, nodesPerSegment = 4, Fmax, Fmin = −Fmax })` finds the force that takes a Model from its start state `x0` to rest at the origin, angle states compared modulo 2π. It uses nothing but `model.f`, so it plans whatever plant the block sees.

- **The sample grid.** The force is held over `hold` = ⌈5 ms / Ts⌉ samples (1 at 10 ms, 5 at 1 ms): still a zero-order hold on the controller's grid, but the work grows with T, not with T / Ts (at Ts = 1 ms the default plan took 13.7 s and slices of 13 ms; now 3.1 s and 3 ms). A segment has P = max(4, round(T / (hold·Ts·segments))) held steps, `perSegment` = P·hold samples, and T is snapped to it (2.4 s = 12 segments × 20 samples × 10 ms). The force is the piecewise-linear interpolation of `nodesPerSegment` nodes per segment, **read at each held step and held over it**: exactly what the Controller applies. RK4 with ⌈hold·Ts / min(5 ms, 0.5 / bound)⌉ substeps per held step; `sub` (2 at 10 ms) is per sample, for the replay along the plan and the check.
- **Unknowns**: the nodes and the states at the starts of segments 1 … M−1 (multiple shooting; 137 for the triple pendulum). **Residuals**: the defects between segments and the miss at the end (angles wrapped), both weighted by the stage; the effort λ·F and the change between neighbouring nodes λ·(F_k+1 − F_k); a hinge 3·(max(0, F − Fmax) + max(0, Fmin − F)), each side its own limit (a one-way-heavy actuator, −5 to 25 N, gives the plan −3.75 to 18.75 N; with min(−u min, u max) it had ±3.75 and no plan). Without the change term the last stage settles on a spiky force, often at the limit (28 N steps of 9 N per sample for the triple pendulum); with it the plan is smooth and needs about half the force (15.5 N, steps of 3 N), leaving the feedback room.
- **Levenberg–Marquardt** on JᵀJ accumulated from per-segment blocks: a segment's end depends only on its start and its own five nodes, so a Jacobian costs 13 one-segment integrations per segment (forward differences, one entry perturbed in place). In the order per segment (its start state, its nodes; the last node at the end) JᵀJ is banded, at most 2n + nodesPerSegment from the diagonal (20 for the triple pendulum), so the solve is a banded Cholesky, nz·bw² instead of nz³/6: 40 segments plan in 3.8 s, not 25.8 s, with slices under 10 ms instead of 150 ms. JᵀJ and the band are preallocated; nothing is allocated in the loops.
- **Continuation stages** (λ, weight, cap): (3·10⁻³, 1, 120), (10⁻³, 10, 80), (3·10⁻⁴, 100, 80). A stage ends when the plan is feasible (defect < 10⁻⁶, end < 10⁻³) or stalls (cost down less than 0.1 % over 4 accepted iterations); what it leaves of its cap goes to the next stage. 300 iterations over all starts.
- **Three fixed starts**, tried in order until one is ok: the states on a straight line from x0 to the origin (angles the short way), the force a·sin(kπt/T) with k = 3, 2, 4. a = ½·min(Fmax, 2·D·(2π/T)²/b), D the largest distance to go and b the smallest nonzero input gain at x0: 15 N for the triple pendulum. No randomness, no clock: the same inputs give the same plan, bit for bit.
- **ok** when the defect is below 10⁻⁴, every angle and position ends within 0.02 (rad, m) and every rate (a unit per second) within 0.5, and the force stays within 1.05 of each side's limit. Otherwise `plan-not-converged`, with a sentence and a hint from the numbers, naming the side it hits ("no plan found within the limit: it needs F up to 10.5, of the 2 it may use (300 iterations, 1 start)", or "down to −6.1, of the −3.75" · "needs more force or a longer T (now 2.4 s)"; "the segments do not join" · "more segments or a longer T"). The best attempt is returned all the same, so it can run and be seen. The plan reports `Flo` and `Fhi`, the force's extremes.
- **Ticks**: `yield null` after each segment's Jacobian columns, after each solve and each trial step, and per segment while a stage's first cost is computed (the first run is cold); one progress object `{ stage, stages, iteration, cost, defect, terminal, fraction, start, starts }` per iteration. `fraction` is per start: a quarter from the stage and iteration, three quarters from how far (in log) the defect and the end have come towards feasible; it never goes back and stays below 100 % until the plan is done (stage 3 often ends early, and a share by stage alone sat at 66 % and then jumped). The loopnote adds "(start 2 of 3)" after the first start.
- **Measured** (Node, on a loaded 4-core machine): the default triple pendulum plans in 2.8–3.5 s, 204 iterations from the first start, peak 15.5 N of the 30 N it may use. The longest slice between yields is under 11 ms of CPU once the code is warm (the cold first run also counts V8 compiling it). The robustness matrix (`npm run test:slow`: T = 1.8 s and 3 s, masses ×2, rods ×1.6, a 4 N push mid-swing, rod masses 10 % lighter or heavier than planned for) plans from the first start and holds in every case, in 156–225 iterations.

Along the plan: `alongPlan(model, plan)` (and `alongPlanSteps`, a generator that ticks per segment) integrates each segment from its shooting start (never one long open-loop replay) and takes Ad_k, Bd_k as central differences of the one-sample step map (the force held, the same RK4), so no c2d. `tvlqrGains(along, { Q, R, Pend })` runs the discrete Riccati recursion backwards from the upright LQR's P, symmetrising P each step. `alongPlan` also takes C_k = ∂y/∂x at x*_k (`Cy`), and `planValues` gives the measurements along the plan Y_k = y(x*_k) and the gains in measurement order K_k = Kx_k C_k⁻¹, so a sensor whose slope changes along the swing (an encoder's error, y = θ + 0.2 sin θ) is read with its slope there, not the origin's; a singular C_k is refused (`states-not-measured`). `planLaw(values, Ts, { start, umin, umax })` is the law (u = 0 until `start`, u = F_k − K_k (y − Y_k) along the plan with angle errors wrapped, then u = kr r − Kup y), and `verifyLoop(model, law, { Ts, sub, duration, umin, umax, d })` runs the nonlinear closed loop and says whether every state ends within reach of the origin (angles 0.05 rad, rates 0.5, other states 0.25), with the worst state, the peak force asked for and the cart's largest excursion.

Where this differs from the plan (§8.3): the end is weighted like the defects (with weight 1 the effort term held it about 0.01 off and the plan never became feasible); a smoothness term (above); unused stage budget carries over (masses ×2 needs about 130 iterations in the last stage); the hinge keeps one weight (one that grows with the stages, or a tanh bound on the force, made the plans worse); the starting amplitude is generic (a Model knows no total mass or g); the law and the mapping to measurements live in `planner.js`, beside the plan they follow. The default plan takes about 3 s in Node, not quite the 2.5 s targeted. After the review: the banded solve, the held force for short Ts, the asymmetric hinge and C_k along the plan (above).

### The `trajectory` type (step 9)

`trajectoryDesign(p, ctx)` in design.js; inputs T (2.4 s), segments (12), planShare (0.75), start (0 s), Q, R, limits. The first three are flagged `heavy, tune: false` and sit in the Controller tab's Plan fold.
1. The upright LQR at the origin by `lqrDesign` (so it refuses what LQR refuses: every state must be measured), x following r. Refuses `bad-limits` unless u min < 0 < u max.
2. The plan: `ctx.heavy('plan', { version, T, segments, Fmin, Fmax }, generator)`, Fmin = planShare · u min and Fmax = planShare · u max: the plan may use a share of each limit, and a limit is a plan input (the review: with one symmetric bound, planShare · min(−u min, u max), a −5 to 25 N actuator gave the plan ±3.75 N). The generator runs `planTransfer` then `alongPlanSteps` (`yield*`), so the along-plan data is kept with the plan. The heavy entry is keyed by these, the plant, the block and Ts, never by Q, R or start: tuning those re-runs steps 3–5 in about 50 ms (TV-LQR, the mapping, the check), never the plan; a limit plans again (the Controller tab says so). The sync store (Node, the CLI) drains the generator at once; the page's store runs it in the background (below). Either keeps 8 plans (LRU); `stats().heavyRuns` counts plans.
3. TV-LQR with Qx = Cᵀ diag(Q) C ending in the upright P, then `planValues`.
4. `verifyLoop` on the nonlinear plant with the law as it runs, `planLaw(values, Ts, { start })` from t = 0 (u = 0 until start), with the limits, until 1 s after the plan. (It ran the plan from t = 0 before: with start 0.5 s and a start state that is not at rest, the triple pendulum read "Verified" while it tumbled.) With start > 0 and a start state that moves under u = 0, a warning: "the plant does not rest at its start state, and the plan assumes it does until start (1 s): start at 0, or start the plant at rest".
5. Rows: a sentence ("Planned in 3.2 s (204 iterations, start 1 of 3). Verified: at rest at the origin 1 s after T, peak F 15.49 (limits -40 to 40)."), T and its grid, F(t) as a sparkline (≤ 120 points, noted "-14.3 to 15.49, of -30 to 30 it may use"), the end error per state, the defect, "K at the origin", kr and the slowest pole: the type plans for any plant, so no row says "upright". The status's `at` reads "θ1, θ2, θ3 = 3.142 rad → origin". A plan that did not converge, or a loop that does not hold, gives status `warn` with the planner's sentence and hint (or "the loop does not hold: θ2 is 0.4 rad off 1 s after the plan; peak F 77 (limits -40 to 40): lengthen T or raise the limits"), and still runs.

The law (`make`) is `planLaw(values, Ts, p)`: u = 0 until `start`, then the plan with TV-LQR, then the upright LQR, angles modulo 2π, clamped. values: F (per sample), Y and K (per sample and measurement), Kup, kr, angle flags; they never reach a file (`computes` refuses F, Y, K, Kup and kr: "they are never kept in a file"), and there is no Copy as numbers. In the Computed box a row with `spark` draws a sparkline and a row with `sentence` reads in the UI font; long design times show in seconds.

`node cli.mjs design <project> [--block <path>] [--json]` prints the same statuses, synchronously; `node cli.mjs new --system <name>` writes a System library entry as a project, and `node cli.mjs systems` lists them.

## Designed variants

A designed type adds `designed: true`, `version`, `computes` (keys refused in a file: "lqr computes K and kr from the plant and Q, R and track; to set them by hand use Copy as numbers (a State feedback variant)"), `twin` (the hand type Copy as numbers makes), `design(p, ctx)` (pure, synchronous; throws `DesignError`; may return pending once the page store is async), `make(p, Ts, values)` (values null → u = 0), `manual(p, values)` (Copy as numbers) and, for the page, `compatible(a, b)`. `makeLaw(variant, Ts, lib, values)`. Parameters may be `nullable` (vectors too: null means "from the plant"), `int`, `positive`, take a `min` and a `max`, and may be flagged `heavy` (it starts a plan) and `tune: false` (auto-tune leaves it alone). A type without a hand twin (`trajectory`) refuses its computed keys with "they are never kept in a file". `ctx` = `{ Ts, idPath, name, kind, inputs, model(), linearize(op, limits), trim(targets, limits), heavy(kind, inputs, start) }`; `heavy` keeps the value of a generator (a plan) under its own key and returns `{ status: 'ready', value, ms }`. A design may return its own `at` (the operating points, for the status) when one label does not say it. A designed law runs as its Copy as numbers twin would (`make` builds the twin's law from `manual(p, values)`), so the copy runs bit for bit alike. A vector parameter's `per` (`'measurement'`, `'level'`) lets the Controller tab name its entries.

| Type | Inputs | Computes |
|---|---|---|
| `lqr` (built) | Q (one per measurement, or one for all), R, track (the measurement r applies to; 0 none), Tr, limits | Discrete LQR at the origin: K = Kx C⁻¹ in measurement order, kr (static gain 1 from r to the tracked measurement; equals K[0] for the carts), the slowest pole. Refuses `states-not-measured` (naming what is missing: "sees x, θ, v but not ω (cart and pole)"; the rank on the equilibrated C), `q-length`, `not-at-rest`, `kink`, `not-stabilisable`, `no-states`, `too-many-states`. `not-stabilisable` says why by PBH tests at each mode with \|z\| ≥ 1: one u does not move keeps the wiring hint; one no weight sees says "Q gives no weight to x, and a mode seen only there does not decay by itself (\|z\| = 1)" · "give x a weight above 0" (the cart's position with Q = [0, 50, 1, 1]). Reproduces the gains the library held (K_SINGLE, K_TRIPLE, K_TRIPLE_GENTLE) to the digits they were stored with (within 0.02 %) |
| `swingUpLqr` (built) | the hand energy-pump gains (kE, kx, kv, θs), Q, R, limits | The catch gains K, kr by `lqrDesign` at the origin (the upright rest), x following r; and the pole's l and g the pump measures energy with (`poleOf`: at the top a rigid pendulum on a cart has θ̈ = (g/l) θ − ẍ / l, so the v̇ and ω̇ rows give l, its effective length, and g/l). They were stored as 0.5 and 9.81, a copy of the cart–pole's own; a longer pole now gets its own. l and g in a file are refused (`computes` K, kr, l, g). Refuses `swing-inputs` unless the block measures four signals with an angle second (the law reads x, θ, v, ω), `swing-plant` when the plant is not one pendulum on a cart. Copy as numbers: `swingUp` (with l and g) |
| `scheduledPI` (built) | levels `at` of the first measurement (one level: a fixed PI), Tcl, Tr, limits | At each level: `trim` → `linearize` → `firstOrderFit` → `piCancel`: Kp = τ/(K·Tcl), Ki = 1/(K·Tcl). u0: the input that holds the first measurement where the plant starts (a `trim` at y1(x0)), so the loop starts in exact balance. The dead time θ is shown and left out, with a warning. The status's `at` reads "h = 0.1 … 1 m (5 levels)"; a `gains` row is a table (level, trim u, K, τ, θ, Kp, Ki). Refusals come from trim, the slopes and the fit (`u-limit`, `trim-failed`, `kink`, `integrating-plant`, `unstable-plant`, `zero-gain`). The store (`createDesignStore`) caches in memory only (64 designs, 8 model compiles, LRU), keyed by the type, its version, the variant's inputs, Ts, the plant (`plantKey`: without places, flips, Sinks' names or the variants of Controller blocks; Observers whole) and the block's id path. Failed designs are cached too: the same inputs fail the same way. compileDiagram calls `store.begin(diagram, compileModel)` once per compile (with Controllers and Observers running laws, designed or not), then `job.resolve(block, variant, lib)` per block, observers first: a designed observer's `values.stateIndex` lets a later Controller look through it. Each resolve gives a status `{ path, block, variant, type, key, status, ms, cached, at, seen, rows, warnings, error, progress }` whose `values` are not enumerable (a status prints and serialises without numbers). `seen` ("F → x, θ, v, ω · 4 states (x, v, θ, ω)") is built from the live labels, so renaming a Sink renames u without a re-design. `simulateSystem(…, { designs })` and `evaluateSystem(p, { designs })` take a store and return the statuses as `info.designs`. Without one, compileDiagram uses `defaultDesigns()`: `SYNC_DESIGNS` in Node, the CLI and tests; in the page its own async store, named with `useDesigns(store)` (also `app.designs`), as a **guest**: a guest compile reads the designs and plans the store holds and the jobs it runs, but starts no job and drops none (`begin(diagram, compile, { guest: true })`). So a compile on main's Auto-tune or Live paths that names no store never plans on the main thread, and shares the page's cache; the page lists them with `window.loopTuner.designs()`. A cache hit costs about 0.2 ms per compile (the triple pendulum's key). The plan's key leaves out Q and R, so tuning Q re-runs only TV-LQR.

### In the page: the plan in the background (step 10)

`createDesignStore({ mode: 'async', debounceMs = 150 })` is the page's store; Node, the CLI and tests use the sync one. Results never depend on the mode: a job is the same generator the sync store drains, so the run after a plan made in slices equals the sync run bit for bit (test 11).
- **A heavy miss** queues one job per heavy key, and the design comes back pending (it is not cached). Its status is `pending` (no values: u = 0, an observer zero estimates), or `stale` when the block's slot (`idPath#variant name#type`) holds the values that ran last and they fit (the same number of measurements and Ts, or the type's `compatible(before, here)`): the previous plan keeps running, labelled. A status waiting on a job carries the job's `progress` (`{ stage, stages, iteration, cost, defect, terminal, fraction, start, starts }`).
- **Debounce**: a job starts 150 ms after it was first asked for, so wheeling a mass plans once. **Newest wins**: every compile with laws ends with `job.end()`, which drops the jobs that compile did not ask for (an edited plant, another variant, Off).
- `runJobs(budgetMs)` works on the oldest job for about budgetMs (the planner yields every few ms) → `{ busy, finished, waitMs }`. A finished job keeps its value as a heavy entry and bumps `generation`. `busy()`, `queue()`, `onProgress(fn)` (at most 10 times a second), `idle()` (a promise: nothing queued), `cancel(key)` and `retry(key)` (a status's key). A cancelled plan stays cancelled (u = 0, or the previous plan) until the block's inputs give a new key or `retry`; both bump `generation`.
- **The pump** (`app.js`): while the store is busy, a MessageChannel message per slice (setTimeout would clamp to 4 ms), a timer during a debounce wait. A slice lasts as long as the browser was away since the last one, 24 to 40 ms, and meanwhile the display and the plant's view draw at most 20 frames a second (`app.frameMs()`, 50 ms; the sweep keeps real time): what runs while a plan is made is u = 0 or the previous plan, so the plan gets most of the main thread. (Before the review the slices were 8 to 16 ms between full-rate frames, and a software-rendered page gave the plan 20 to 35 % of the thread.)
- **The acquisition key** includes `generation`, so a settled job makes the next acquire compile again. **Settle** (the light path): `display.restartSweep()` keeps the run so far faded and starts the sweep at the window's start, the display takes the new run, the Computed box and the loopnote follow, and a toast says "Swing-up planned in 4.1 s" (the job's title from `ctx.heavy(…, { title })`). The Controller tab's inputs are not re-rendered: a field being typed in keeps its focus and text. An Auto Scale made while a design was pending (when a system loads) is made again on the new run, unless the scope was set by hand in between.
- **Progress** patches only the bar and line in the Computed box, the variant glyph ("⟳ 43 %") and the loopnote ("planning 43 %", "re-planning 43 %", "planning 12 % (start 2 of 3)", "planning cancelled"), so the box's Cancel button stays put. The box's buttons (Cancel, Plan, Copy as numbers) are bound inside the box by `data-act`, never by a tab-wide id: the Plan button once shared `ct-plan` with the Plan fold, so it did nothing and opening the fold re-planned.
- `window.loopTuner.whenDesigned()` resolves, with the statuses, once nothing is queued and the display shows the run that uses the result.
- **Measured** in headless Chromium on this loaded 4-core machine (after the review): Node plans the triple pendulum in 2.8 to 3.5 s; the page, from loading the system with the Plant tab's view sweeping, in 4.8 to 6.9 s (6.1 s with the Controller tab open). The page's animation frames come 33 times a second, 50 ms apart at the 95th percentile; the only long tasks (60 to 210 ms) are loading the system and the settle. A Web Worker stays out (decisions, v2.7.1): plans are below the 10 s that would call for one. (Before: Node 4.8 s, the page 7 to 22 s.)

**The Controller tab** (built in step 7):
- A read-only **Computed** box: an LCD readout beside the parameters when the column has room, below them when it has not (the plan said below; beside keeps K in view while Q is wheeled). It shows the status, the time or "cached", and the key (#682b37); the method and operating point; the plant seen; the values (gains labelled by measurement, a table for the PI at three digits, kr, poles, θ, u0); the warnings; for an error its message, hint and "Until then the block puts out u = 0". `controllerTab.renderComputed()` patches only this box and the variant glyphs, for designs that settle on their own; `renderProgress()` only a plan's progress. While a plan is made the box shows a progress bar with the stage, iteration, cost and defect, what runs meanwhile, and **Cancel**; once cancelled, **Plan**; for a stale status the previous plan's rows follow.
- **Copy as numbers** (for any type with `manual`) inserts "<name> (numbers)" after the variant and runs it; toast "Copied: these numbers no longer follow the plant." A field left untouched is not committed on blur, so its rounded display never replaces the copied full-precision numbers.
- **Variant glyphs**: "computed"; on the running variant "! no design" (red) or "! computed" (amber, a quality warning), "⟳ 43 %" while a plan is made, "cancelled".
- **Library** in two groups, From the plant and By hand (no type is filtered out).

## For the Analysis tab (step 12)

The Analysis tab is its own workstream (on main: `core/analysis.js`, `ui/analysis.js` and `design/output/analysis.md`). It forms the open loop cut at a Controller's output u, L(z) = −C_y(z) P(z) (C_y: the law's measurement columns; negative feedback), from two models this layer gives, both from the same compiled diagram that runs.

- **Snapshots.** `simulateSystem(diagram, signals, sim, { designs, until: t })` runs to the sample nearest t (within the window; the run so far comes back as usual) and adds `snapshot: { t, X, held, inputs, sources }` (`el.snapshot`): the full state X in the global order, what each Controller holds (`held[idPath]`: its u) and each Observer (its estimates), what each read at its last sample (`inputs[idPath]`: [r, y…] or [u, y…]), and the Sources' values. `null` when the run diverged before t. Dead times keep their history out of X; a model passes them straight through. It fits a model directly: `el.seen(idPath, { X, held, sources, t })`.
- **The plant**: `linearizeBlock(project, idPath, at = 'origin', { designs, limits })` in `project.js` → the LinearModel of `linearize` (`{ A, B, C, D, n, m, states, outputs, input, op, delay, sensors, warnings }`, continuous, matrices as arrays of rows; B n×1, C m×n, D m×1) plus `idPath`, `Ts` (the block's) and, for `{ t }`, `t` (on the simulation grid).
  - `at`: `'origin'`, `'initial'`, `{ y: [levels] }` or `{ t }`. The plant is the one the block sees, looking through designed observers as its design did.
  - `{ t }` runs the system to t with the given store (the page's, so a plan is never made twice) and builds the Model there; u is what the block put out (an Observer: what its input u read). `op.drift` and a warning say how far from rest it is.
  - `limits` (for a trim) default to the running variant's u min and u max.
- **The law**: every controller type has `linear(p, Ts, at, values)` → `{ A, B, C, D }`, the discrete state space at Ts from [r, y1 … ym] to u (B nc×(m+1), C 1×nc, D 1×(m+1)), valid while u is inside its limits. The prefilter Tr lies outside the loop and is left out. `at = { y, t }`: the measurements at the operating point and the time of the run the law is at.
  - Hand types: `off` (0); `pid` (the integral; with Kd the filtered derivative and the previous y); `stateFeedback` (kr, −K); `gainScheduled` (the PI with the gains at y1: at rest the schedule's slope multiplies a zero error); `swingUp` (state feedback where it catches, |θ| < θs; elsewhere it throws: "pumps energy").
  - Designed types give their twin's model from their values, since they run as their twin: `lqr` (state feedback), `scheduledPI` (`pid`, or `gainScheduled` at y1), `swingUpLqr` (the catch). `trajectory`: u = 0 before `start`; along the plan the gains of the sample at t, r unused, with a `note` that they are frozen; after the plan, and at rest (no t), the upright LQR. Without values: `DesignError` `no-design`.
  - Each matches its `step()` for small moves about the operating point to 1e-12 (1e-5 for the scheduled PIs, whose slope term is second order).
- **The loop**: `loopModel(project, idPath, at, { designs })` → `{ plant, ctrl, Ts, opLabel, variantName, type, t, warnings }`, the shape main's Analysis tab reads through `app.loopModel(path, op)`, which `app.js` provides with the page's store; agents get the same from `window.loopTuner.loopModel(path, op)`.
  - The law's `at.t` is the snapshot's time, 0 for `'initial'`, none otherwise.
  - Warnings add to the model's: u at a limit there ("q = 0 is at its limit (0 to 3) there: the controller saturates, and the linear loop does not hold"), estimates looked through ("the estimates of 'estimator' are read as the states they stand for: the filter's own dynamics are not in this loop"), and the law's note.
  - Refusals (`DesignError`, with a sentence and a hint): `no-diagram`, `no-block`, `not-a-controller`, `no-design` (a plan not made yet, or the design's own refusal), `not-linear` (a swing-up pumping energy), `diverged`.
- **Discretising is the tab's job** (`discretePlant` on main): a zero-order hold at Ts, and each measurement's `delay[k]` as round(delay / Ts) unit delays, exact when the dead time is a whole number of samples (the tank's 0.1 s pipe at 20 ms).
- **Checked** (`test/loop.test.mjs`): the linear loop formed this way follows the nonlinear run. The cart–pole on LQR from 0.01 rad matches to 1e-6 m. The tank's scheduled PI with a 1 cm step at 0.45 m, through the pipe's 5 samples of dead time, matches to 0.07 mm. The cart–pole loop's poles equal LQR's own to 1e-9. The snapshot run equals the full run bit for bit up to t.
- **Not yet**: an Observer's own dynamics in the loop. A Controller on a Kalman filter's estimates sees the states they stand for, and the observer types have no `linear`; L through the filter needs it as part of the controller, with u fed to it from the cut.

Where this differs from the plan (§12): `linear` takes `at` before `values`, `linear(p, Ts, at, values)`, the contract main's Analysis tab already uses for the hand types (`at.y` for the scheduled PI and the swing-up). `loopModel` and `el.snapshot`'s `inputs` and `sources` are additions: the first is what main's tab asks `app.loopModel` for, the second gives an Observer's u and the Sources at t.
