## 2026-10-24 · v2.7: time control, after review

Two reviews of the first build (no new words from the person). What changed, and the interpretations it took:

- **∞ runs at the simulation's own speed, and no setting runs faster.** The page times the screen's simulation after each change (screen seconds over the wall time it took; the fastest of up to three timings, the later two only while the speed is held to it, as the first is slowed by the browser compiling). Found in review: ∞ swept a screen per frame, so its figure was the screen's length times the frame rate (0.55× on a 10 ms screen, 646× on a 50 s one), not a limit of the system. Interpretation: the sweep replays one simulation, but it is paced as if it were simulating, so the readout tells how fast the page can run the system ("show how fast the time is actually running"). Consequence, said plainly: the simulation takes 2000 steps for any screen, so the limit depends on the time per division, and a screen the page simulates slower than real time (the oven at 1 ms/div: 0.7×) runs below 1× at every setting. **Ask the person** (roadmap.md, open questions); this revises "As fast as possible completes each sweep in a frame" below.
- **A finite speed keeps time on short screens**: a frame that ends a sweep goes on into the next, round the screen as often as it takes, and all of it counts (it was capped at one sweep a frame: 1× ran at 0.59× on a 10 ms screen). Found in review.
- **Auto-tune's runs last their own length** (one period of the input) at the speed, not the screen's sweep: a 5 s run takes 5 s at 1× on a 1 s or a 10 s screen (it ran at 4.5× and 0.67×). **The next run is computed while one sweeps** and starts in the frame the one before ends, so 10× reads 10× (it was 8×). At ∞ a slice of computing stops before a step would overrun it, an improvement is its own task at most four times a second, and the tuner's run stands for the screen's when they are the same simulation. **The display stops for every method**, so at ∞ the readout counts the tuner's computing (relay and step showed the screen's replay). **The scope's Stop stops the tuning** while a run sweeps (it skipped to the next run). A run on the display pauses while the tab is hidden, as the sweep does. Found in review; the pacing details are ours.
- **At ∞ only a changed run fades the earlier ones**, so after an edit, or at the end of Auto-tune at ∞, the run before stays to compare (it was gone within five frames). At a finite speed every sweep still fades them, as the person set (five runs); whether high speeds should count only changed runs too is open.
- **The control**: six digits and a field wide enough for them; a number too large to hold (`1e400`) is refused, not taken for ∞; Esc goes back to the speed from before the field took the focus, the arrows' steps included; one header menu open at a time (Speed ▾, System library ▾, Save ▾). **Held at 1× by a live plant**: read-only in the secondary ink (not faded), a lock at the field's left, and a click or tap says why in a toast, so touch users see the reason too; the readout keeps a fixed width, so nothing moves on Connect. The readout's tooltip gives the simulation's speed; "caps out" is no longer in the page's text.
- **The autosave is written when the page is closed or reloaded**, not only 300 ms after a change.
- For agents, `loopTuner.speed()` also returns `simulation`, the simulation's speed.
